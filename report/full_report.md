## 3. 精度对比：官方 PyTorch vs Rust

### 3.1 判定标准（为什么要引入尺度归一化）

单一**绝对阈值** max|Δ| ≤ 1e-4 只在数据量级 O(1~100) 时成立。本次新增的 Electricity 数据源预测值峰值达 **9.3e4**，此处 **一个 float32 ULP 就是 7.8e-3**，任何实现之间必然出现远大于 1e-4 的绝对差。因此本报告采用 5 级判定：

| 判定 | 条件 | 含义 |
|---|---|---|
| EXACT | 全部元素逐位一致 | 完全一致 |
| TOL | max\|Δ\| ≤ 1e-4 | 绝对噪声级 |
| TOL_SCALE | max\|Δ\| > 1e-4，但 **量程归一化误差** ≤ 1e-5 | 数据幅值导致的绝对误差，非缺陷 |
| WARN | 量程归一化误差 ∈ (1e-5, 1e-4] | 数值漂移偏大，但在量程 0.01% 内，需关注 |
| FAIL | 量程归一化误差 > 1e-4 | 真实语义/数值分歧 |

> **量程归一化误差** = max\|Δ\| / (max(官方预测) − min(官方预测))，即误差占预测值动态范围的比例，与数据量级无关。

典型例证：`electricity_h96` 绝对误差 5.86e-3（超出 1e-4 阈值 59 倍），但该场景预测值峰值为 1.05e4、单个 float32 ULP = 9.77e-4，**5.86e-3 仅相当于 6 个 ULP**，量程归一化误差 5.6e-7 —— 相对精度反而优于 ETTh1（1.1e-6）。

| S1 单变量小样本 | 1 | 96 | 381 | 573 | **0.67×** | 640 | 675 |
| S2 基线 7x1024 | 1 | 96 | 2816 | 2237 | **1.26×** | 2523 | 3065 |
| S3 长视野 h720 | 1 | 720 | 3295 | 3457 | **0.95×** | 4690 | 5184 |
| S4 宽表 24x1024 | 1 | 96 | 10581 | 6486 | **1.63×** | 7572 | 7137 |
| S5 长上下文 3072 | 1 | 96 | 8995 | 7748 | **1.16×** | 8787 | 5846 |
| S6 batch4 7x1024 | 4 | 96 | 10308 | 9032 | **1.14×** | 7887 | 7174 |

**规律**：加速比随**问题规模增大而上升**——单变量小样本（S1，1×512）与长视野（S3，h=720）上 Rust 与官方互有胜负（Rayon 调度开销 / 自回归解码步数占主导）；到了宽表（S4 宽表 24x1024）场景，自研 cache-tiled GEMM + 分块并行优势最大，达到 **1.63×**。这与 §4.1 全矩阵 1.16× 的整体结论一致：全矩阵 211 个场景里有 **189 个** Rust 更快。

**量化档为何反而更慢**：FP16 档在每次 GEMM 前需把权重 tile 由 f16 解包为 f32，在 CPU 上这部分开销大于省下的内存带宽，因此纯延迟维度 FP32 仍最优；FP16 的价值在于**体积减半**（§5）与内存受限场景。

### 4.3 冷启动（进程启动 → 加载 → 首次预测，端到端墙钟）

| 实现 | 3 次测量 (ms) | 中位数 |
|---|---|--:|
| 官方 PyTorch | [8783, 11373, 9623] | **9623 ms** |
| Rust FP32 | [2623, 2625, 2722] | **2625 ms** |

冷启动优势 **4×**：官方需导入 torch 动态库并把 1.32 GB 权重完整读入进程内存；Rust 侧为 mmap 零拷贝映射 + 静态链接单文件。

## 7. 测试过程中发现并修复的缺陷

### 7.1 [P1] FP16 量化 GEMM 在单线程环境下退化到标量循环

**现象**：线程扩展性测试中，`RAYON_NUM_THREADS=1` 时 FP16 档位耗时 **204 s**，而同形状 FP32 仅需 **5.2 s**（慢 39×）；2 线程以上 FP16 完全正常（3.3 s）。小形状同样复现（1×512：14.9 s vs 0.64 s，慢 23×）。

**根因**：`src/ops/gemm.rs` 的 `gemm_f16_portable` 原有分支为

```rust
if num_threads <= 1 || (m * k * n) < 20_000 {
    gemm_tail_cols_f16(a, b, c, m, k, n, 0, n);   // 标量三重循环
    return;
}
```

`gemm_tail_cols_f16` 是**无 SIMD、无缓存分块**的三重循环，且内层对每个元素单独做 `f16 → f32` 转换；而多线程路径走的是 `_mm256_cvtph_ps` 批量解包 + `matrixmultiply::sgemm`（BLIS 微内核）。即：**线程池一旦只有 1 个 worker，量化路径就整体退化**——这不是并行度损失（否则只应慢 N 倍），而是切换到了另一条实现。

**修复**：移除 `num_threads <= 1` 短路，单线程只是拿到更少的 tile，仍走 SIMD + BLIS 路径（`num_chunks = min(n/128, max(threads,1)*2)`）。

| 场景（单线程，7×1024 / h96） | 修复前 | 修复后 | 提速 |
|---|--:|--:|--:|
| FP16 全量 | 204,019 ms | **8,252 ms** | **24.7×** |
| FP16 balanced | 183,591 ms | **8,635 ms** | **21.3×** |
| FP32（对照） | 5,159 ms | 5,707 ms | — |
| FP16 1×512 / h96 | 14,857 ms | **1,658 ms** | **9.0×** |

修复后 FP16 单线程与 FP32 单线程的比值（8.3 s / 5.7 s ≈ 1.45×）落在合理区间——量化档需额外做权重解包，略慢于原生 FP32 属预期。

> 该缺陷仅影响**量化档位 + 单线程部署**（如容器限制 1 核、`RAYON_NUM_THREADS=1` 的嵌入式场景）。本报告 §4.4 的线程表为修复后重测数据。

## 8. 结论与后续建议

| 维度 | 结论 |
|---|---|
| 精度 | 与官方 PyTorch **数值等效**：191/211 场景（90.5%）误差在噪声级；残余差异与**官方自身在不同线程数下的自噪声同量级**（官方 2.44e-3 vs Rust 5.86e-3），已触及可达下限 |
| 速度 | 全矩阵 **1.16×**，189/211 场景更快；宽表最高 1.63×；冷启动 **4×** |
| 资源 | 峰值内存基本持平；部署体积从 934 MB（Python + torch）降到 **0.74 MB 单文件** |
| 风险 | 20 个 WARN/FAIL 全部落在**退化合成输入**（零方差 / 全负值 / 跨量级）与 100% 缺失列场景，真实业务数据源 0 FAIL |

**后续建议**

1. **对齐退化输入的 eps 处理**（P2）：与官方逐算子比对 RevIN 方差估计、线性去趋势回归、make_positive 在零方差 / 全负值输入下的分支，消除 `synth_flat` 家族的语义分歧。
2. **补齐量化档的端到端收益**（P2）：FP16 当前只省体积不省时间，建议把权重解包结果按 tile 缓存复用，或评估 f16 原生累加（BF16/FP16 SIMD）路径。
3. **扩大真实数据源覆盖面**（P3）：补充 Weather、ILI、M4 等公开集，以及带外生协变量的场景，进一步压低「只在合成集上分歧」的残余风险。
4. **把本次矩阵接入 CI**（P3）：211 场景全量约 25 分钟，可作为 nightly 回归，用 TOL/TOL_SCALE 计数做阈值门禁。
